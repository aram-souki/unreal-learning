# Unreal Engine Learning — Domain Model

## Glossary

**Curriculum Scope** — An unanchored tour of Unreal Engine subsystems, not a single game concept. Covers: graphics, physics, game logic, testing, CI/CD, scenes, and code deployment, taught via industry-standard practice rather than isolated tutorials. Hands-on from the start: a real project, real repo, real builds, real CI/CD — not conceptual-first.

**Hybrid Development Approach** — The chosen split of implementation language: C++ for core systems and performance-critical code, Blueprints (visual scripting) for designer-facing scripting and fast iteration. Chosen because it's the real-studio norm, and because it's the only approach where "testing," "CI/CD," and "deployment" have concrete meaning (Blueprint-only projects have limited unit-test and command-line-build support).

**Learner Background** — Solid C++, plus Python/C# and general application-development experience. No prior game engine of any kind (first exposure to Unreal or any engine). This curriculum itself is solo, but is explicitly meant to transfer afterward to a **small team of 3** — so process/tooling decisions (version control, hosting) should hold up at that later team scale, not just for one person.

**Application-Dev vs. Real-Time-Simulation Paradigm** — The core conceptual gap for this learner. Application development (Python/C#/typical app work) is largely event-driven: code runs in response to discrete requests/events and is otherwise idle. Game development runs a persistent frame/tick loop: every actor in the scene gets a chance to update every frame, driven by delta-time, with physics and rendering recalculated continuously regardless of user input. Curriculum should call this out explicitly before/while introducing Actors, Components, and Tick.

**Toolchain** — Unreal Engine 5.8.4 (installing). Editor/IDE: Cursor/VS Code, not the Visual Studio IDE. Underlying C++ compiler: lean **Build Tools for Visual Studio** (MSVC + Windows SDK only, no full Visual Studio IDE) — needed because Unreal's build system (UnrealBuildTool/UnrealHeaderTool) generates projects and invokes MSVC but does not bundle it; Epic doesn't redistribute Microsoft's proprietary toolchain.

**Target Platform** — Windows only. Other platforms (Linux, console, mobile) are explicitly out of scope; they'd add cross-compilation/signing/store setup without teaching new Unreal deployment concepts.

**Testing Scope** — Both, deliberately split by what each is good for: Unreal's **Automation Framework** (Simple/Complex/Functional/Spec tests, runs in-engine, required for anything touching actual gameplay/level state, runnable headless via `UnrealEditor-Cmd.exe ... -ExecCmds="Automation RunTests X" -unattended`) for engine-dependent behavior, and plain **C++ unit tests** (Catch2/GoogleTest) for pure game-logic classes deliberately decoupled from the engine runtime, for fast feedback. Gauntlet (device-farm/multiplayer session automation) is noted as existing but out of scope — not needed for a solo learning project.

**Version Control** — Git + Git LFS (not Perforce), hosted on GitHub or GitLab (not self-hosted, not local — must support remote access for the later 3-person team, not just this machine). LFS tracks binary asset types (`.uasset`, `.umap`, etc.) as pointers in git history while storing actual content in separate LFS storage, avoiding repo bloat from binary diffs. Perforce ruled out for two compounding reasons: server-administration overhead that teaches Perforce-ops rather than Unreal for a solo learner, *and* no genuinely free hosted option once this transfers to the 3-person team (Perforce's free tier is for a self-administered server, not hosted service). Git+LFS is "free with a ceiling" instead: GitHub's free LFS quota is 1 GB storage / 1 GB bandwidth per month (small — real Unreal assets will exceed it, at which point it's ~$5/50GB data packs); GitLab's free LFS quota is more generous (10 GB) if staying fully free longer matters more than the GitHub ecosystem. **Chosen host: GitHub** — reused by the deferred self-hosted-Actions-runner CI idea, and 1 GB free LFS is enough to get through the learning phase.

**Project Structure** — One single growing project, not a series of disconnected per-subsystem exercises. Subsystems (graphics, physics, logic, testing, CI/CD, scenes, deployment) are added incrementally to the same project so they interact realistically (e.g. physics affecting what's rendered, logic reacting to collision events), rather than being learned in isolation.

**Project Concept** — A third-person character in a small sandbox level: moves around, interacts with physics objects, collects items toward a simple objective. Deliberately unambitious — a vehicle for touching every subsystem (scenes = the level, graphics = materials/lighting, physics = interactable objects/collision, logic = collecting/scoring, testing = unit-test the scoring logic + Automation Functional test that collecting in a loaded level updates state, deployment = package a Windows build), not a design exercise in itself. Matches Unreal's own starter-template shape so we're not fighting engine defaults.

**Skill Capture Practice** — Each time we build/test a new concept (not a whole subsystem bucket — individual concepts like "Actor/Component tick model" or "Automation Functional Tests"), create a project-scoped Claude skill (`.claude/skills/<topic>/SKILL.md`, via the skill-creator skill) right after, capturing terse working notes specific to this project (decisions, gotchas, what broke) rather than a rehash of Unreal's own docs. Chosen fine-grained rather than per-subsystem so each skill stays small enough to be a useful lookup later.
